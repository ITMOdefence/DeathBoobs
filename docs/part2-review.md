# Проверка требований части 2

Область проверки — модель данных, кодек, Database API и RAM-индексы.
Рабочая ветка: `data-model`. Настоящие Storage, Transaction, журналирование
и интеграция приложения относятся к частям 1/3 и не заменяются тестовыми fake.

## Соответствие исходному заданию

| Требование | Реализация и проверка |
| --- | --- |
| GameSession и Detection | `records.h`: все поля, явные bool-признаки наличия, принадлежащая модели ссылка на кадр |
| Fixed-point, единицы и пределы | Публичные константы в `records.h`, значения и примеры в `records.md` |
| Независимое бинарное представление | `record_codec.c`: ручной little-endian, версия записи 1, точные длины, flags/reserved и канонические значения |
| Open/close, start/finish, save, lookup | `database.h` и `database.c`; проверяются результаты и неизменность выходов при обычных ошибках |
| История через callback | По одной записи, порядок `(timestamp, detection_id)`, остановка по ошибке visitor, без результирующего массива всей истории |
| Выборка по времени | Глобальный замкнутый интервал `[from, to]`, включая равные границы и пустые результаты |
| Index по session ID и detection ID | Отсортированные массивы с двоичным поиском позиции |
| Группировка по session ID | Отдельный index `(session_id, timestamp, detection_id)` |
| Восстановление при open | Один проход страниц Storage; проверка replay, затем публикация рабочего объекта |
| Storage/Transaction границы | Только публичные функции, без `libfile`, без определения внутренней структуры Storage в production коде |
| Transaction пока fake | Публичный `transaction.h`; fake в `tests/fakes/`, подключаемый только тестовой сборкой |
| Без частичной публикации | Validation/reserve до Transaction; ID и все indexes публикуются только после commit; ошибки откатываются |
| Ошибка rollback/cleanup | Handle остаётся только для close/retry; исключение failed-open cleanup явно описано в `database.h` |
| Переполнения и границы | Проверены размеры массивов, длины ссылок, ёмкость буфера, независимое исчерпание обоих ID без wrap |
| PUNos ErrorCode | Используется существующий ABI `<sys/core.h>`, новые номера ошибок не добавлены |
| Формат Storage сохранён | `format.h`, `storage.h` и `storage.md` не меняются; records используют только payload |
| Запрещённые расширения | SQL, универсальные схемы/таблицы, B+ tree и сетевой сервер не добавлены |
| Freestanding сборка | `-Wall -Wextra -Werror`, проверка реальных объектов при `-O0/-O2` без скрытых libc memory symbols |
| Рабочий каталог | Runner создаёт build artifacts во временном каталоге и удаляет их при выходе |

## Unit tests

`tests/unit/codec/record_codec_test.c` содержит 11 групп: независимые byte
fixtures, encode/decode обеих моделей, все optional-комбинации, границы,
каждый обрезанный prefix, повреждения длины/flags/reserved/значений,
неподдерживаемые kind/version, неверные аргументы и сохранность выходов.

`tests/unit/database/database_test.c` содержит 16 групп. Покрыты создание
и завершение сессии, сохранение обнаружения, отсутствующая сессия, lookup,
история и интервалы, visitor stop/reentrancy, reopen, оба переполнения ID,
ошибки Storage/Transaction и памяти, рост index, повреждённый replay,
отсутствие записи/потраченного ID после ошибки и повторный close при ошибках
rollback/освобождения памяти. Дополнительно проверяются неверный физический
Page ID от Transaction и ошибка чтения после уже доставленного префикса
истории с последующим успешным повтором обхода.

Оба набора используют реальные PUNos types/ErrorCode headers; только
неподготовленные runtime-зависимости подменены fake. Fake сохраняет страницы
при close/reopen в том же процессе; это не тест физической сохранности файла.

```sh
sh tests/run.sh
CC=clang DEATHBOOBS_SANITIZE=1 sh tests/run.sh
```

Если checkout PUNos не соседний `../PUNos`, задаётся `PUNOS_ROOT`.

## Проверки, ожидающие интеграции

В текущем checkout нет реализации Storage и `tests/unit/storage/`, поэтому
требование о прохождении существующих Storage tests здесь проверить нельзя.
Их необходимо запустить после подключения части 1. CRC, настоящий I/O,
журналирование, crash recovery и блокировка файла также не подтверждены
этими unit tests; это интеграционные критерии частей 1/3.

Index строится в RAM и в худшем случае требует квадратичного времени replay;
вставка занимает `O(n)`. Ранняя версия хранит одну запись на физическую страницу.
Ограничения производительности и единицы измерений согласуются с приложением
до сохранения реальных данных, без молчаливого изменения версии формата.
