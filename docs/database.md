# Database API и индекс в памяти

Публичный интерфейс части 2 объявлен в `include/deathboobs/database.h`,
реализация находится в `src/database/database.c`. Модели, единицы измерения,
диапазоны и бинарный формат записей описаны в [records.md](records.md).

Database использует только публичные `storage.h`, `transaction.h`, кодек
записей и PUNos `libmem`. Он не вызывает `libfile` и не знает внутреннего
устройства `DeathboobsStorage`. Формат страниц Storage не изменён.

## Операции и владение

| Функция | Назначение |
| --- | --- |
| `deathboobs_database_open` | открыть/создать Storage и восстановить индекс |
| `deathboobs_database_close` | освободить индекс и закрыть Storage |
| `deathboobs_database_start_session` | назначить ID и сохранить ACTIVE-сессию |
| `deathboobs_database_finish_session` | добавить FINISHED-снимок той же сессии |
| `deathboobs_database_save_detection` | назначить ID и сохранить обнаружение |
| `deathboobs_database_get_session` | найти сессию по ID и прочитать её актуальную страницу |
| `deathboobs_database_get_detection` | найти обнаружение по ID и прочитать его страницу |
| `deathboobs_database_visit_session_history` | последовательно прочитать историю одной сессии |
| `deathboobs_database_visit_detections_between` | прочитать обнаружения всех сессий за `[from, to]` |

`DeathboobsDetectionInput` содержит поля обнаружения без `id`: Database сам
выделяет ID. Приложению не нужно подставлять временный ID или специальное
число вместо необязательного значения. Все признаки наличия и канонические
нулевые хвосты соответствуют правилам `records.h`.

Результаты lookup, start и save публикуются только при успехе. Обычно ошибка
open также оставляет выходной указатель нетронутым. Есть одно исключение,
необходимое для владения ресурсами: если после неудачного открытия сама
очистка ресурсов завершилась ошибкой и ресурсы остались, `out_database`
получает объект только для повторного close, а open возвращает ошибку очистки.
Такой объект нельзя использовать для чтения или изменения данных. Удобно
инициализировать указатель базы значением NULL перед первым open и при ошибке
закрыть его, если он стал ненулевым.

Close с ненулевым адресом и NULL handle — успешная пустая операция. Ошибка
close не всегда означает, что объект сохранился: Storage может сообщить
ошибку flush, уже закрыв свой handle. Нужно проверять итоговый указатель;
ненулевой объект допускает только повторный close. Ошибка освобождения
индекса оставляет его MemoryBlock действительным до следующей попытки.

## Валидация и жизненный цикл

Сессия создаётся ACTIVE. Завершение требует существующую ACTIVE-сессию,
`finished_at >= started_at` и время не раньше последнего обнаружения этой
сессии. Повторное завершение и запись в FINISHED-сессию возвращают
`CORE_INVALID_STATE`.

Обнаружение требует существующую ACTIVE-сессию и `timestamp >= started_at`.
Неправильные ID, диапазоны fixed-point, признаки наличия и размеры ссылок
отклоняются до Transaction. Отсутствующий ID возвращает `CORE_NOT_FOUND`,
нулевой ID или неверный аргумент — `CORE_INVALID_ARGUMENT`. Ошибки кодека,
Storage, Transaction и памяти передаются вызывающему коду.

Сессии и обнаружения используют независимые возрастающие ID, начиная с 1.
После сохранённого `DEATHBOOBS_ID_MAX` следующая операция создания
соответствующего вида возвращает `CORE_OVERFLOW`; перехода через ноль нет.
Неудачная запись не расходует ID.

## Публикация изменений и Transaction

Каждая операция изменения сохраняет одну новую страницу с одной записью.
Завершение сессии добавляет новый снимок, сохраняя ID и время начала.

Порядок операции:

1. Проверить аргументы, состояние и переполнения.
2. Подготовить закодированную страницу и зарезервировать память индексов.
3. Начать Transaction, добавить страницу и выполнить commit.
4. После успешного commit обновить все индексы и выходной результат.

После commit не выполняется выделение памяти, которое могло бы помешать
публикации уже сохранённой записи. Резервная ёмкость массива может увеличиться
даже при неудачной операции, но логические записи и ID остаются прежними.

При ошибке append или commit Database вызывает rollback. Ошибка rollback
имеет приоритет над исходной ошибкой и переводит базу в состояние, допускающее
только close; close повторяет rollback. Пока откат не завершён, нельзя
продолжать работу со Storage через тот же объект.

`transaction.h` — граница с частью 3. Успешный commit потребляет handle;
неудачный commit обязан сохранить handle для rollback. Контракт не допускает
возврата ошибки после уже успешной фиксации: неоднозначный результат commit
потребует отдельного согласованного протокола. Настоящие rollback journal,
восстановление после аварии и блокировка файла в этом checkout отсутствуют.

## Устройство индекса

В памяти поддерживаются четыре динамических массива:

- сессии по `session_id`: последний снимок, Page ID и максимум времени
  обнаружений с отдельным признаком наличия;
- ссылки на обнаружения по `detection_id`;
- ссылки по `(session_id, timestamp, detection_id)` для истории сессии;
- ссылки по `(timestamp, detection_id)` для общего интервала времени.

Ссылка содержит ID обнаружения, ID сессии, timestamp и Page ID. Тела всех
обнаружений в индексе не хранятся. Lookup ищет позицию двоичным поиском и затем
читает и декодирует страницу через Storage, проверяя соответствие индексу.

Поиск позиции занимает `O(log n)`, вставка со сдвигом — `O(n)`. Ёмкости
начинаются с 8 элементов и обычно удваиваются; размер выделения проверяется
на переполнение. Расход памяти равен размеру объекта Database плюс
`session_capacity * sizeof(SessionEntry)` и сумме ёмкостей трёх массивов
обнаружений, умноженной на `sizeof(DetectionEntry)`. Это внутренние структуры,
а не часть публичного ABI. Служебные расходы выделителя памяти сюда не входят.

Open проходит страницы ровно один раз в порядке Page ID, но вставка в
отсортированные массивы даёт в худшем случае квадратичное время восстановления.
При больших объёмах понадобится отдельная оптимизация построения индекса;
постоянный индекс или B+ tree в эту реализацию не входят.

При replay первый снимок сессии должен быть ACTIVE. Разрешён ровно один
переход ACTIVE → FINISHED с неизменным started_at и корректным временем конца.
Обнаружение не может предшествовать созданию сессии, идти после её завершения,
ссылаться на отсутствующую сессию или повторять ID другого обнаружения.
Некорректные страницы/записи не публикуют частично восстановленный рабочий
объект. Поддерживаются только страницы сессий и обнаружений версии записей 1;
пока отсутствуют соглашения об обработке metadata и index pages, их типы
возвращают `CORE_UNSUPPORTED`.

## Последовательное чтение

Оба visitor API передают по одной записи в порядке `(timestamp, detection_id)`.
Таким образом, равные timestamps имеют однозначный порядок. Границы временной
выборки включены; `from > to` отклоняется. Известная сессия без обнаружений
завершает обход без вызова visitor; неизвестная возвращает `CORE_NOT_FOUND`.

Callback получает временный заимствованный снимок; для удержания его нужно
скопировать. Контекст может быть NULL. Возврат любого кода, кроме `CORE_OK`,
останавливает обход и передаётся вызывающему коду. Ошибка чтения после
нескольких вызовов callback оставляет уже доставленный префикс истории.
Сборка всей истории в отдельный результирующий массив не выполняется.

Из callback разрешены lookup-вызовы. Изменения, close и вложенный visitor
возвращают `CORE_INVALID_STATE`. API однопоточный; приложение сериализует
вызовы. Поддержка нескольких процессов, одновременных писателей или
многопоточного доступа не заявляется.

## Тестовые зависимости и запуск

`tests/fakes/` предоставляет только тестовые реализации Storage, Transaction
и используемых операций libmem. Реальные заголовки типов, ErrorCode, String
и MemoryBlock берутся из PUNos. Production Database не подставляет fake
автоматически: для приложения нужны настоящие Storage/Transaction/libmem.

Fake хранит один логический store в памяти процесса; все непустые пути
обозначают его. Close/reopen сохраняет страницы, reset удаляет их. Это позволяет
проверять повторное построение индекса, но не является тестом файловой
совместимости, CRC, настоящего I/O или сохранения между процессами.

Fake Transaction отдельно держит одну страницу и проверяет ошибки append,
flush и commit до публикации. Он не пытается откатывать физический файл через
несуществующий Storage truncate. Fault injection покрывает операции Storage,
Transaction, выделение памяти и освобождение непустого MemoryBlock. Счётчик
MemoryBlock помогает проверять очистку; память самого fake store/handles
учитывается отдельно выделителем хоста и очищается при close/reset.

Из корня репозитория:

```sh
sh tests/run.sh
```

По умолчанию ожидается соседний checkout `../PUNos`. Иное расположение задаётся
переменной `PUNOS_ROOT`, компилятор — `CC`. Тесты собираются на 64-битном хосте
с `-std=c11 -Wall -Wextra -Werror -ffreestanding`; временные бинарники создаются
вне репозитория и удаляются при выходе. Для AddressSanitizer и
UndefinedBehaviorSanitizer:

```sh
CC=clang DEATHBOOBS_SANITIZE=1 sh tests/run.sh
```

Перед unit tests `tests/check_freestanding.sh` компилирует настоящие production
объекты без libc и fake-зависимостей при `-O0` и `-O2`, затем проверяет через
`nm` точный список внешних символов. Для кодека внешних символов быть не должно;
Database разрешены только используемые публичные операции кодека,
Storage/Transaction и libmem. `NM` позволяет выбрать инструмент проверки
символов. Это проверка объектных зависимостей, а не запуск PUNos runtime или
полная линковка с ещё отсутствующими частями 1/3.

Внутренние `src/internal/bytes.h` обеспечивают копирование/обнуление RAM
явными volatile byte loops: aggregate initialization/assignment компилятор
может превратить в libc `memcpy`/`memset` даже с `-ffreestanding`, а в PUNos
этих символов нет. Эти операции никогда не сериализуют модель; файл по-прежнему
получает только вручную закодированные little-endian поля.

Проверки включают жизненный цикл сессии, сохранение и поиск обнаружений,
сортировку истории, замкнутые интервалы, reopen, исчерпание ID, повреждённые
данные и ошибки зависимостей с проверкой отсутствия частично опубликованных
записей. Реальные Storage tests пока не входят в этот checkout; их нужно
подключить при интеграции с частью 1.
