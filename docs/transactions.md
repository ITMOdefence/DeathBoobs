# Транзакции DeathBoobs

## API

- `deathboobs_transaction_open(database_path, journal_path, &storage)` открывает базу и выполняет восстановление до передачи `Storage` вызывающему коду. Закрытие через `deathboobs_storage_close(&storage)`.
- `deathboobs_transaction_begin(storage, journal_path, &tx)` проверяет отсутствие журнала и временного файла, синхронизирует исходное состояние базы и начинает транзакцию. Если журнал или временный файл уже есть, возвращает `CORE_ALREADY_EXISTS`. Для уже открытого `Storage` предусмотрен `deathboobs_transaction_recover(storage, journal_path)`.
- `deathboobs_transaction_page_write(tx, &page)` копирует переданную существующую страницу в память. Чтение через `Storage` до начала `commit` видит исходные данные. При повторной записи того же ID применяется последняя версия, в журнал попадает одна исходная страница.
- `deathboobs_transaction_page_append(tx, &page, &id)` резервирует следующий ID и добавляет страницу атомарно вместе с остальными изменениями транзакции.
- `deathboobs_transaction_commit(&tx)` фиксирует все подготовленные страницы. Пустая транзакция завершается без журнала.
- `deathboobs_transaction_rollback(&tx)` освобождает подготовленные страницы и при наличии опубликованного журнала восстанавливает исходные данные.
- `deathboobs_transaction_recover(storage, journal_path)` повторяет восстановление при необходимости. Отсутствие журнала допустимо. Вызов синхронизирует каталог, в том числе после предыдущего удаления, для которого синхронизация могла завершиться ошибкой.

Передавайте `NULL` в качестве `journal_path`, чтобы использовать `<путь базы>.journal`. Явно переданный путь должен побайтно совпасть с этим именем. Временный файл называется `<путь базы>.journal.tmp`. Оба имени зарезервированы и должны находиться в том же контролируемом приложением каталоге, что и база.

Держите `Storage` открытым до завершения транзакции. Между `begin` и успешным `commit` или `rollback` вызывайте операции записи только через Transaction. Во время фиксации, отката и обработки их ошибок вызывающий код должен исключить доступ к страницам через Storage. Вызывайте методы одного экземпляра последовательно.

Успешный `commit` или `rollback` обнуляет `tx`. При ошибке указатель сохраняется. До успешного `storage_flush()` в `commit` можно повторить `commit` или начать `rollback`. После успешного flush базы и перехода к очистке повторяйте `commit`, даже если удаление журнала или синхронизация каталога вернули ошибку. После начала отката повторяйте `rollback`. Если основная операция и закрытие файла завершаются ошибками, API возвращает исходную ошибку. `file_close()` PUNos освобождает handle и при ошибке, поэтому следующая попытка при необходимости открывает файл заново.

## Фиксация и восстановление

1. `commit` создаёт временный файл, записывает заголовок и исходные версии всех изменяемых страниц. Записи отсортированы по ID.
2. `commit` вызывает `file_flush()`, закрывает временный файл, переименовывает его в `*.journal` и синхронизирует родительский каталог. Прерванная запись временного файла безопасна, поскольку до публикации и синхронизации журнала основной файл ещё не изменялся.
3. `commit` при необходимости расширяет файл, записывает изменённые и добавленные страницы через внутренний транзакционный путь Storage и вызывает `deathboobs_storage_flush()`.
4. `commit` удаляет журнал и синхронизирует родительский каталог. Успех возвращается после обеих операций. Если в момент сбоя удаление ещё не закрепилось на накопителе, при открытии возможны два сценария. Сохранился журнал — восстановится старое состояние. Журнал отсутствует — сохранится полностью записанное новое состояние.

Восстановление сначала проверяет весь опубликованный журнал. После проверки оно синхронизирует каталог, чтобы имя журнала было устойчивым и при сбое самого восстановления. Затем вторым последовательным проходом переписывает исходные страницы через Storage и синхронизирует базу. После закрытия журнала удаляет его и синхронизирует каталог. Пока журнал существует, повторное восстановление заново пишет те же исходные версии. Временный файл, оставшийся до публикации, удаляется при успешной обработке открытия.

Обрезанный журнал, неверный CRC, размер записи или порядок ID дают `CORE_IO_ERROR`. Неизвестная версия корректного заголовка даёт `CORE_UNSUPPORTED`. Несовпадение идентификатора файла даёт `CORE_INVALID_STATE`. В этих случаях опубликованный журнал сохраняется, а восстановление завершается до первой записи в базу. Если I/O ломается во время записи при восстановлении, журнал сохраняется для следующей попытки.

## Формат журнала 1.0

Все многобайтовые поля записаны в little-endian. Размер опубликованного файла точно равен `64 + N × 4096` байт. `N` — число исходных изменяемых страниц; для транзакции, состоящей только из добавлений, оно может быть нулём. CRC использует CRC-32/ISO-HDLC с отражённым полиномом `0xEDB88320`, начальным значением и финальным XOR `0xFFFFFFFF`.

### Заголовок

| Смещение | Размер | Поле |
| ---: | ---: | --- |
| 0 | 8 | Байты `44 42 4A 52 4E 4C 00 00` |
| 8 | 2 | Major, `1` |
| 10 | 2 | Minor, `0` |
| 12 | 4 | Размер записи, `4096` |
| 16 | 8 | Идентификатор устройства базы, `st_dev` |
| 24 | 8 | Inode базы, `st_ino` |
| 32 | 8 | Число страниц данных базы на момент `begin` |
| 40 | 8 | Число записей, `N` |
| 48 | 8 | Итоговое число страниц после успешного `commit` |
| 56 | 4 | CRC-32 всех 64 байт заголовка с нулём в этом поле |
| 60 | 4 | Зарезервировано, нули |

### Запись

Каждая запись — исходная страница данных в том же бинарном представлении, которое описано в [формате Storage](storage.md#4-страница-данных). Байты записи формирует общий кодек, поля C-структуры кодируются явно.

| Смещение в записи | Размер | Поле |
| ---: | ---: | --- |
| 0 | 8 | ID страницы в диапазоне от 1 до числа страниц данных. ID возрастают строго |
| 8 | 2 | Тип страницы |
| 10 | 2 | Флаги |
| 12 | 4 | Размер полезной нагрузки от 0 до 4064 |
| 16 | 8 | Поколение |
| 24 | 4 | CRC-32 всех 4096 байт записи с нулём в этом поле |
| 28 | 4 | Зарезервировано, нули |
| 32 | 4064 | Полезная нагрузка и нули до конца записи |

## PUNos и границы поддержки

- Storage удерживает эксклюзивную блокировку Linux OFD на inode от открытия до закрытия. Повторное открытие через Storage возвращает `CORE_WOULD_BLOCK`. В пределах процесса одновременно разрешена одна транзакция или одно восстановление. Блокировка кооперативная, произвольные программы могут писать в обход неё.
- Поддерживается локальная файловая система Linux x86_64 с OFD-блокировками, атомарным переименованием в одном каталоге и рабочим `fsync` файла и каталога. Путь базы, её inode и устройство должны сохраняться до завершения восстановления. Перенос, подмена, удаление базы и ручная правка файлов журнала в этот период находятся за пределами протокола. Storage требует обычный файл, не поддерживает жёсткие ссылки на базу или символическую ссылку в последнем компоненте пути.
- Транзакция перезаписывает существующие страницы и добавляет новые. При откате или восстановлении добавленные страницы удаляются усечением файла до исходного размера. Прямые операции записи Storage во время активной транзакции запрещены. Подготовленные изменения занимают одну страницу памяти с небольшими служебными данными на каждый записанный ID.

## Сборка и тесты

`make all PUNOS_DIR=/path/to/PUNos` включает транзакции в существующий архив `libdeathboobs_storage.a`. Требуемая ревизия PUNos зафиксирована в `punos.ref`.

- `make check PUNOS_DIR=/path/to/PUNos` запускает исходные тесты Storage и интеграционный тест Transaction с библиотеками PUNos. Интеграционный тест проверяет блокировку из второго процесса и аварийный выход после записи первой страницы и после flush базы до удаления журнала.
- `make check-host PUNOS_DIR=/path/to/PUNos` запускает исходные тесты Storage, интеграционные сценарии и тесты отказов. Тестовый backend моделирует видимое состояние после сбоя процесса и состояние с учётом подтверждённых операций синхронизации после потери питания.
