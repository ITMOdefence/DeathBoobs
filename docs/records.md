# Модель данных и формат записей

Этот документ фиксирует первую версию прикладных записей части 2. Модели
объявлены в `include/deathboobs/records.h`. Публичный кодек объявлен в
`include/deathboobs/record_codec.h`, реализация — `src/codec/record_codec.c`.
Database API и индекс реализованы в `src/database/database.c`, публичная граница —
`include/deathboobs/database.h`. Контракт Transaction объявлен в
`include/deathboobs/transaction.h`; пока используется только тестовый fake.
Правила владения, индексов и интеграции описаны в [Database API](database.md).

Версия записи независима от версии Storage. Заголовок файла, формат страниц,
CRC и публичные `format.h` / `storage.h` не меняются. Размеры ниже описывают
последовательность байтов, а не `sizeof` C-структуры.

## 1. Типы, единицы и пределы

Все границы включительные, если явно не указано иное. Публичные константы
определены в `records.h`; база не принимает `float` или `double`.

| Поле | Тип модели | Единица / смысл | Диапазон |
| --- | --- | --- | --- |
| `GameSession.id` | `DeathboobsSessionId` (`u64`) | ID сессии | `1 .. 18446744073709551615` |
| `Detection.id` | `DeathboobsDetectionId` (`u64`) | ID обнаружения | тот же диапазон |
| `Detection.session_id` | `DeathboobsSessionId` | ссылка на сессию | тот же диапазон |
| `Detection.target_id` | `DeathboobsTargetId` (`u64`) | необязательный внешний ID цели | тот же диапазон, если присутствует |
| `started_at`, `finished_at`, `timestamp` | `DeathboobsTimestamp` (`u64`) | миллисекунды от Unix epoch, UTC | `0 .. 18446744073709551615` |
| `x`, `y` | `i32` | миллиметры в локальной системе координат | `-1000000 .. 1000000` на каждую ось |
| `azimuth` | `u32` | сотые доли градуса по часовой стрелке от севера | `0 .. 35999` |
| `distance` | `u32` | миллиметры | `0 .. 1000000` |
| `confidence` | `u16` | вероятность, умноженная на `10000` | `0 .. 10000` |
| `frame_reference_size` | `u16` | число значимых байтов ссылки | `1 .. 256`, если присутствует |

`DEATHBOOBS_ID_MIN/MAX` применяются ко всем трём видам ID.
`DEATHBOOBS_TIMESTAMP_MIN/MAX` и `DEATHBOOBS_TIME_UNITS_PER_SECOND` задают
представление времени. Для координат и расстояния определены отдельные
`*_UNITS_PER_METRE` и `*_MIN/MAX`; для азимута — `*_UNITS_PER_DEGREE`
и `*_MIN/MAX`; для уверенности — `DEATHBOOBS_CONFIDENCE_SCALE` и `*_MIN/MAX`.
Длина ссылки ограничена `DEATHBOOBS_FRAME_REFERENCE_MIN_BYTES/MAX_BYTES`.

Примеры: `x = -1250` означает `-1,250 м`, `distance = 12345` — `12,345 м`,
`azimuth = 9050` — `90,50°`, `confidence = 8750` — вероятность `0,8750`
или `87,50 %`. Азимут `36000` недопустим: север кодируется как `0`.

Ось `x` направлена на восток, `y` — на север. Приложение выбирает начало
координат один раз на сессию и не меняет его внутри сессии. Эти координаты
не являются пикселями или географической широтой/долготой. Положение камеры
и метаданные начала координат в версии 1 не хранятся. Если они нужны для
интерпретации истории, приложение хранит их отдельно с привязкой к session ID.
Проверка геометрического соответствия координат, азимута и расстояния не
выполняется: исходные данные вычисляет приложение.

Преобразование из других единиц и округление выполняются до вызова Database.
Промежуточное умножение и сложение проверяются на переполнение. Отрицательное
время, значения до Unix epoch и значения вне указанных диапазонов не принимаются.

## 2. Необязательные поля и владение памятью

| Поле | Признак наличия в модели | Бит в записи |
| --- | --- | --- |
| `GameSession.finished_at` | `has_finished_at` | session flags, бит 0 |
| `Detection.target_id` | `has_target_id` | detection flags, бит 0 |
| `Detection.frame_reference` | `has_frame_reference` | detection flags, бит 1 |

Только признак наличия определяет, существует ли значение. В частности,
`finished_at = 0` может быть присутствующим временем Unix epoch. Значения
`-1`, нулевой ID или пустая ссылка не заменяют отдельный признак наличия.

Каноническое представление отсутствующего `finished_at` или `target_id` —
нулевое поле при сброшенном бите. При отсутствии ссылки её размер и весь
буфер равны нулю. При наличии ссылки размер равен `1 .. 256`, а неиспользуемый
хвост буфера модели заполнен нулями. Неканонические модели отклоняются до
кодирования; декодер обнуляет неиспользуемый хвост.

Ссылка — принадлежащий структуре массив байтов, а не указатель. Нулевой
терминатор не добавляется и не входит в длину. Байты могут содержать `0x00`;
база не проверяет текстовую кодировку и не трактует ссылку как путь. Приложение
задаёт её смысл и хранит кадр отдельно. Владелец записи не должен поддерживать
жизнь внешнего буфера. Остальные измерения обязательны; отсутствующие измерения
нельзя подменять специальными числами.

## 3. Сессии, идентификаторы и порядок истории

`DeathboobsSessionStatus` содержит ровно два допустимых значения:

- `DEATHBOOBS_SESSION_STATUS_ACTIVE = 1`: `has_finished_at = false`;
- `DEATHBOOBS_SESSION_STATUS_FINISHED = 2`: `has_finished_at = true`
  и `finished_at >= started_at`.

Нулевая или неизвестная величина статуса недопустима. Завершение сессии
не меняет её `id` и `started_at`. Повторное завершение и добавление обнаружения
в завершённую сессию — ошибки состояния. При завершении Database дополнительно
проверяет, что `finished_at` не раньше любого сохранённого обнаружения сессии.

Обнаружение ссылается на существующую активную сессию, имеет
`timestamp >= started_at` и после сохранения неизменно. Внешний `target_id`
не требует наличия отдельной таблицы целей. Поздно поступившие обнаружения
могут иметь время меньше ранее сохранённых обнаружений той же активной сессии.
История упорядочивается по `(timestamp, detection_id)` по возрастанию и
передаётся через callback/visitor. Интервал времени замкнутый: `[from, to]`,
обе границы включены; `from > to` недопустимо.

Сессии и обнаружения имеют независимые возрастающие последовательности ID.
Первый ID каждого вида равен `1`; одинаковые числа между видами допустимы.
Database восстанавливает наибольший ID каждого вида при открытии. Если максимум
равен `DEATHBOOBS_ID_MAX`, последовательность исчерпана: следующая операция
создания возвращает `CORE_OVERFLOW`, без вычисления переполняющего `max + 1`.
ID цели назначает приложение. Даты и ID никогда не вычисляются с переполнением.

Для append-only хранения завершение добавляет новый снимок сессии с тем же ID.
При восстановлении индекса допустим переход от одного ACTIVE-снимка к одному
FINISHED-снимку с неизменным `started_at`. В индекс попадает последний корректный
снимок в порядке Page ID. Остальные повторения ID сессии, обратный переход,
нарушение времени и повторяющиеся ID обнаружений считаются повреждением данных.

## 4. Общий заголовок записи версии 1

Все многобайтовые числа кодируются вручную в little-endian. `u8` записывается
одним байтом. Отрицательные координаты имеют 32-битное two's-complement
представление; например, `-1` — `ff ff ff ff`. Нельзя использовать прямую запись
структур, битовых полей, C enum или `bool`, а также невыровненные обращения к
целочисленным указателям. Размеры C-структур и их padding не являются ABI файла.

| Смещение | Размер | Поле | Значение |
| ---: | ---: | --- | --- |
| 0 | 1 | `kind` | `1` — GameSession, `2` — Detection |
| 1 | 1 | `version` | `1` |
| 2 | 2 | `flags` | биты наличия для соответствующего вида |
| 4 | 4 | `record_size` | полный размер записи, включая 8 байт заголовка |

Номера `kind` относятся к записям, а не к `DeathboobsPageType`. Все неописанные
биты flags обязаны быть нулевыми. Неизвестная версия не интерпретируется как
версия 1 и не пропускается молча. Существующие значения kind и version нельзя
переопределять; несовместимое изменение полей требует новой версии записи.

## 5. GameSession: 40 байт

| Смещение | Размер | Поле |
| ---: | ---: | --- |
| 0 | 8 | общий заголовок: kind = 1, version = 1, record_size = 40 |
| 8 | 8 | `id`, u64 |
| 16 | 8 | `started_at`, u64 |
| 24 | 8 | `finished_at`, u64; ноль при отсутствии |
| 32 | 1 | `status`: 1 или 2 |
| 33 | 7 | reserved: нули |

Единственный допустимый бит flags — `0x0001`, наличие `finished_at`.
ACTIVE требует flags = `0x0000`; FINISHED — flags = `0x0001`.
Проверяются диапазоны ID, reserved, статус и согласованность времени/flags.

## 6. Detection: 60 + N байт

| Смещение | Размер | Поле |
| ---: | ---: | --- |
| 0 | 8 | общий заголовок: kind = 2, version = 1, record_size = 60 + N |
| 8 | 8 | `id`, u64 |
| 16 | 8 | `session_id`, u64 |
| 24 | 8 | `timestamp`, u64 |
| 32 | 8 | `target_id`, u64; ноль при отсутствии |
| 40 | 4 | `x`, i32 |
| 44 | 4 | `y`, i32 |
| 48 | 4 | `azimuth`, u32 |
| 52 | 4 | `distance`, u32 |
| 56 | 2 | `confidence`, u16 |
| 58 | 2 | `frame_reference_size = N`, u16 |
| 60 | N | значимые байты `frame_reference`, без терминатора |

Flags: `0x0001` — наличие `target_id`, `0x0002` — наличие ссылки на кадр.
Допустимы только значения `0x0000 .. 0x0003`. При наличии target ID он не равен
нулю; при отсутствии равен нулю. При сброшенном бите ссылки `N = 0`; при
установленном `1 <= N <= 256`. Неиспользуемый хвост буфера модели в запись
не входит. Размер записи — от 60 до 316 байт. При отсутствии обоих полей
flags = 0, target_id = 0, N = 0, record_size = 60.

## 7. Размещение в Storage и атомарность

В первой реализации одна страница данных содержит одну полную запись:

- GameSession размещается в `DEATHBOOBS_PAGE_TYPE_SESSIONS` (2);
- Detection размещается в `DEATHBOOBS_PAGE_TYPE_DETECTIONS` (3);
- payload начинается с общего заголовка записи;
- `payload_size` в точности равен `record_size`;
- page flags = 0, generation = 0: каждая запись добавляет новую страницу;
- байты страницы после payload равны нулю согласно контракту Storage.

Обе записи помещаются в `DEATHBOOBS_PAGE_PAYLOAD_SIZE = 4064`; разбиения
записи между страницами нет. Запас и reserved-байты не содержат скрытых полей.
Такое размещение упрощает восстановление индекса, но расходует 4096 байт
на запись. Упаковка нескольких записей не входит в этот этап.

Database читает страницы через публичный Storage API, а изменения выполняет
через Transaction. Только успешный commit разрешает публикацию нового ID,
снимка сессии и элементов индекса. Ни кодек, ни модели не вызывают `libfile`
и не обращаются к внутренней структуре `DeathboobsStorage`.

Настоящие commit/rollback/recovery относятся к части 3. До их появления fake
Transaction должен хранить изменения отдельно и атомарно применять их к fake
Storage. Сам Storage не гарантирует атомарности; его текущий API не предоставляет
truncate/rollback. Fake не обещает откат уже записанных физических страниц или
устойчивость к аварийному завершению процесса.

## 8. Проверки и ошибки кодека

Кодек использует `ErrorCode` из PUNos и не вводит собственные числовые коды.
Контракт для encode/decode:

| Условие | ErrorCode |
| --- | --- |
| Успешная операция | `CORE_OK` |
| Нулевой обязательный указатель, недостаточный буфер, обрезанная/лишняя длина, неверные flags/reserved, поле вне диапазона, известный kind передан декодеру другого вида | `CORE_INVALID_ARGUMENT` |
| Неизвестный kind или version при наличии полного общего заголовка | `CORE_UNSUPPORTED` |
| Переполнение при вычислении размера или преобразовании числа | `CORE_OVERFLOW` |

Database использует `CORE_NOT_FOUND` для отсутствующей сессии/обнаружения,
`CORE_INVALID_STATE` для недопустимого перехода состояния и передаёт ошибки
Storage/Transaction вызывающему коду. Повреждённая прикладная запись не должна
становиться успешным результатом открытия. Ошибки данных сохраняют указанные
коды кодека; отдельный код повреждения в ABI PUNos отсутствует.

До чтения полей декодер проверяет наличие полного общего заголовка. Для
поддерживаемого вида и версии он проверяет точный размер, допустимые flags,
все ограничения полей и соответствие `N` доступным байтам. Длина входа должна
точно совпадать с `record_size`; хвостовые байты не игнорируются. Проверки
выполняются до копирования ссылки и публикации результата. Декодирование идёт
во временную модель; encode полностью проверяет модель и ёмкость до записи.
При ошибке выходная модель, буфер и выходная длина остаются неизменными.

Standalone codec проверяет одну запись, но не существование сессии, порядок
снимков, уникальность ID или временные отношения с другими записями. Эти
проверки выполняет Database перед commit и при восстановлении индекса.

Публичные функции `deathboobs_game_session_encode/decode` и
`deathboobs_detection_encode/decode` работают с одним типизированным record.
Encode принимает указатель на модель, буфер, его ёмкость и `out_size`; decode —
буфер, точную длину и указатель на выходную модель. Все указатели обязательны.
Encode меняет только значимые байты результата; хвост доступного буфера остаётся
нетронутым. Константы размера и версии доступны в `record_codec.h`. Для Detection
можно выделить `DEATHBOOBS_DETECTION_ENCODED_MAX_SIZE` байт и использовать
фактический размер из `out_size`.

Буфер байтов не требует выравнивания. Он может пересекаться с памятью модели:
encode сначала готовит полную запись в локальном буфере, decode сначала полностью
проверяет временную модель. `out_size` должен указывать на отдельный объект
`usize`, не пересекающийся с моделью и буфером; выходная модель должна иметь
корректное выравнивание. Кодек не выделяет динамическую память и не вызывает
Storage, Transaction или `libfile`. Размеры версии 1 ограничены 316 байтами,
поэтому после проверки длины ссылки сумма `60 + N` и преобразование в u32
не могут переполниться.

## 9. Границы текущего изменения

Этот этап содержит модели, публичные константы, спецификацию, кодек, Database API
и RAM-индексы с unit tests. Реальные Storage и Transaction пока не реализованы
в этом checkout: тесты связываются с fake Storage/Transaction и адаптером libmem
для хоста. Ни журналирование, ни восстановление после аварийного завершения
не подменяются этими fake-реализациями.
Принятые единицы и пределы — решения версии 1 для начала разработки,
а не ограничения, подтверждённые адаптером камеры. Их нужно сверить с приложением
до сохранения реальных данных; последующая несовместимая корректировка уже
записанного формата потребует новой версии и явной миграции.

## 10. Запуск unit tests кодека

Из корня DeathBoobs при соседнем checkout `../PUNos`:

```sh
sh tests/unit/codec/run.sh
```

Для другого расположения PUNos:

```sh
PUNOS_ROOT=/absolute/path/to/PUNos sh tests/unit/codec/run.sh
```

Тесты используют реальные заголовки типов и ErrorCode из PUNos, но не запускают
его runtime и не подменяют эти типы libc-заголовками хоста. Сборка выполняется
с `-std=c11 -Wall -Wextra -Werror -ffreestanding`. Достаточно C-компилятора хоста;
его исполняемый файл можно выбрать через `CC`. Временный бинарник создаётся вне
репозитория и удаляется при выходе, включая ошибку теста.

Для Clang/GCC с AddressSanitizer и UndefinedBehaviorSanitizer:

```sh
CC=clang DEATHBOOBS_CODEC_SANITIZE=1 sh tests/unit/codec/run.sh
```

Тесты проверяют фиксированные little-endian образцы, обе модели и их границы,
необязательные поля, повреждения, обрезания, неподдерживаемые версии и
сохранность выходных значений при ошибках. Storage tests в текущем checkout
отсутствуют; кодек не изменяет контракт или бинарный формат Storage.
