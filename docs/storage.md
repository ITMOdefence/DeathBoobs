# Файловое хранилище DeathBoobs

## 1. Назначение

Storage — нижний слой DeathBoobs. Он предоставляет доступ к файлу как к последовательности страниц фиксированного размера и не знает о структуре игровых сессий и обнаружений.

## 2. Инварианты

- размер каждой физической страницы равен 4096 байт;
- страница `0` содержит заголовок файла;
- страницы данных нумеруются начиная с `1`;
- размер корректного файла всегда кратен 4096;
- многобайтовые значения записываются в little-endian;
- C-структуры не записываются в файл напрямую;
- каждая страница данных защищена контрольной суммой CRC-32;
- существующая страница перезаписывается только целиком;
- новая страница добавляется только в конец файла;
- Storage не обещает атомарность нескольких изменений — это задача Transaction.

## 3. Заголовок файла

Заголовок занимает физическую страницу `0`. Неиспользуемые байты должны быть равны нулю.

| Смещение | Размер | Поле | Значение |
| ---: | ---: | --- | --- |
| `0` | 8 | Magic | ASCII `DEATHDB\0` |
| `8` | 2 | Major version | `1` |
| `10` | 2 | Minor version | `0` |
| `12` | 4 | Page size | `4096` |
| `16` | 4 | Header size | `32` |
| `20` | 8 | Format flags | `0` |
| `28` | 4 | Header CRC-32 | CRC заголовка при нулевом поле CRC |
| `32` | 4064 | Reserved | Нули |

Количество страниц не хранится в заголовке. Оно вычисляется по размеру файла. Благодаря этому добавление страницы не требует немедленной перезаписи заголовка.

## 4. Страница данных

Каждая страница данных содержит 32-байтовый заголовок и 4064 байта области полезных данных.

| Смещение | Размер | Поле |
| ---: | ---: | --- |
| `0` | 8 | Page ID |
| `8` | 2 | Page type |
| `10` | 2 | Flags |
| `12` | 4 | Payload size |
| `16` | 8 | Generation |
| `24` | 4 | CRC-32 |
| `28` | 4 | Reserved |
| `32` | 4064 | Payload |

CRC-32 вычисляется по всем 4096 байтам страницы при нулевом поле CRC.

`Page ID` обязан совпадать с физической позицией страницы в файле. `Payload size` не может превышать 4064. Байты после полезной нагрузки должны быть равны нулю.

`Generation` увеличивается верхним слоем при логической перезаписи страницы. Storage сохраняет значение, но не определяет правила его изменения.

## 5. Типы страниц

| Значение | Назначение |
| ---: | --- |
| `0` | Недопустимый тип |
| `1` | Метаданные базы |
| `2` | Игровые сессии |
| `3` | Обнаружения |
| `4` | Зарезервировано для будущего индекса |

Неизвестный тип страницы считается ошибкой формата в версии 1.0.

## 6. Открытие файла

При открытии Storage:

1. открывает или создаёт файл;
2. получает его размер и тип;
3. для пустого файла записывает корректный заголовок;
4. для существующего файла проверяет кратность размера странице;
5. читает страницу `0` полностью;
6. проверяет magic, версию, размер страницы, flags и CRC;
7. вычисляет количество страниц данных;
8. публикует готовый `Storage` вызывающему коду.

Частично инициализированный объект не публикуется.

## 7. Чтение страницы

Чтение должно:

- проверить диапазон `Page ID`;
- перейти к смещению `Page ID × 4096`;
- прочитать ровно 4096 байт с учётом коротких чтений;
- проверить идентификатор, тип, размер нагрузки, reserved-байты и CRC;
- декодировать страницу только после полной проверки.

Повреждённая страница никогда не возвращается как успешный результат.

## 8. Запись страницы

Storage кодирует страницу в отдельный временный буфер размером 4096 байт, вычисляет CRC и только после этого вызывает файловую запись.

`storage_page_write()` допускает только существующий `Page ID`. `storage_page_append()` всегда выбирает следующий физический идентификатор и не принимает идентификатор от вызывающего кода.

Вызов `storage_flush()` передаёт изменения накопителю через `file_flush()`.

## 9. Ограничения первой версии

- один процесс;
- один писатель;
- нет списка свободных страниц;
- страницы не уменьшаются и не перемещаются;
- файл не сжимается;
- повреждение страницы обнаруживается, но автоматически не исправляется;
- шифрование не поддерживается;
- атомарность набора страниц обеспечивает отдельный слой Transaction.
